## ADR-002 Dependency Injection with Hilt
### Status: Accepted (In usage currently)

## Problem
The architecture we proposed in  `ADR-001.md` requires that dependencies such as repository , domain are injected to the ViewModels and not initialized directly

## Alternatives
- Manual DI (Constructors): 
  - **PRO's:** Zero Overhead, full control. 
  - **CON's:** Dose not Scale. Manual Factory per each class.
- KOIN: DSL KOTLIN:
  - **PRO's:** Simple Setup
  - **CON's:** Runtime resolution, errors not caught at compile time.
- Dagger 2:
  - **PRO's:**: Performance,Compile Time errors
  - **CON's**: Complex setup and learning.
- ***HILT***
  - **PRO's**:Compile Time , Native integration
  - **CON's:**Annotating process slows down build time.
## Decision
We decided to go with **Hilt 2.52**

Giving us:
-   Compile Time safety: Missing dependencies errors are caught by the KSP Processor duing the build time. Making us a step closer to production.
- ViewModel Integration: @HiltViewModel eliminates boilerplate code of ViewModelFactory. Handling correctly the whole lifecycle.
- Scoping: @Singletone for FirebaseFirestore and FirebaseAuth guarantees one instance of each per process, which is what we need for our db connection.

Structured DI as following:
-   RepositoryModule: binding interfaces to implementations
- AppModule: initializatesFirebase 

## Consequences

### Benefits
  - Zero Nullpointerexcep from not initiated dependencies runtime
  - Test using mock without toching real prod code.
### Accepted TradeOffs
  - KSP annotation processing adds a few seconds to building 
  - Code generated by Hilt is very volumunouse and hard to debug if something goes wrong.
