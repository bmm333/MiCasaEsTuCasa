## AuthRepo and UseRerpo - two separate Repos

## Status
Accepted

## Context

Firebase offers two distntinct services for user handling:
-   **Firebase Auth**: Handles Identity
- **Firestore**: Handles application data (profile,role,badge,rating,etc)

Could've used a simpler approach like an UserManager merging everything together handling
login , signup, profile updating , role reading etc. But that approach then would've violated
SRP and leaving us with a far worse to test and read code.

## Decision
We separated in two Repositories with different responsabilities:
 **AuthRepo**:  Responds to are you authenticated?
          login(email,password)->Result,
 register(email,password)->Result,
logout()->Unit,
currentUserId():String?

**UserRepo**: Responds to who are you and what've you done
getCurrentUser():User?
updateUser(user:User)->Result
getUserById(id:String)->Result

This separation mirrors exactly the separation of firebase services. So if we want to 
change from firbase auth solution to a costum solution or like supabase auth or auth0 , we have to touch only
FirebaseAuthRepo and FirebaseUserRepo remains the same.

## Consequences:

**Pros**
- AuthViewModel depends only on AuthRepo no access to profile data, which is right because it dose not need that
- UserViewModel depends only on UserRepo , cannot do accidentally login/logout 
- LoginUseCase mocks only AuthRepo not the entire user layer
**Accepted Tradeoffs**
- At the moment of signup , need to coordinate two operations: 1 FirebaseAuth creates user 2 Firestore creates the profile doc. If the first succeds but the scond fails, user exists in firebase auth but dose not have a profile in firestore. This is mitigated by a lazy check in `Getcurrentuserusecase` which creates the profile if it dose not exist
**Technical Debt**
- No Transactional Coordination between Auth+Firestore at signup moment.
