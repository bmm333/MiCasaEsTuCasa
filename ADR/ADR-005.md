## ADR-005 Real Time Chat - Firestore SnapshotListener + callbackFlow

### Status
Accepted

## Context
Chat needs real time updates — messages have to show up without the user doing pull to refresh or anything manual. We looked at a few options:

- **Polling every N sec**: easy to implement but latency is bad (N seconds) and Firestore reads pile up fast. Costs go up for nothing.
- **Firebase Realtime Database**: sub second latency yeah but we already have Firestore for everything else, adding another db service just for chat feels overkill and adds complexity.
- **WebSocket custom backend**: best performance wise but we dont have a backend. This is a uni project, we are not deploying a socket server.
- **Firestore `addSnapshotListener`**: sub second latency, cost efficient. No extra infra.

## Decision
We use Firestore `addSnapshotListener` exposed as a Kotlin `Flow` via `callbackFlow`.

`callbackFlow` is the correct builder for converting listener based APIs into Flow — unlike `flow {}`, it supports emissions from callbacks that run on different threads. This is the pattern recommended by JetBrains and used in Firebase Android KTX.

Messages are stored as a subcollection under conversations: `conversations/{conversationId}/messages/{messageId}`. This gives us simpler Firestore security rules and easier queries compared to a flat top level messages collection.

Key implementation decisions:

**`sendMessage` uses batch write** — message document + `lastMessage` update on the conversation doc in one atomic operation. Both succeed or nothing. This avoids the state where the message exists but the conversation preview still shows the old text.

**`markMessagesAsRead` uses batch update with chunking at 500** — Firestore has a hard limit of 500 operations per batch. We chunk the unread messages and batch each chunk separately. For now this is fine.

**`getConversationsForUser` runs two queries and merges client side** — one query for `hostId == userId` and another for `renterId == userId`. Firestore dose not support OR on different fields in a single query so this is the workaround. We dedup by id and resort by lastMessageTimestamp.

**`getOrCreateConversation`** checks if a conversation already exists with matching (hostId, renterId, propertyId) before creating a new one. Business rule says only one conversation per property between two users.

**`awaitClose { listener.remove() }`** is critical in the `callbackFlow` — without this the Firestore listener stays alive in background when the user leaves the chat screen, generating reads we dont need and potentially leaking memory. The Flow cancels automatically when the viewModelScope dies.

## Consequences

**Pros**
- Sub second message delivery. Firestore notifies clients within around 200-500ms from write in normal conditions.
- Listener is efficient: first read brings all messages, after that only deltas are pushed.
- Flow integrates with `viewModelScope` — automatic cancellation when ViewModel is destroyed.
- Batch write guarantees atomic msg + conversation preview update. No inconsistent states.

**Accepted Tradeoffs**
- `getConversationsForUser` with the two queries + client merge is not great if a user has hundreds of conversations. For a uni project its fine but in prod it would not scale.
- Chat repo dose not handle image upload. If the message has an image, the caller is responsible for uploading to Firebase Storage first and then passing the url to `sendMessage`. No progress tracking on uploads.

**Technical Debt**
- The two query merge for conversations could be replaced with a denormalized `participants: List<String>` field on the conversation doc, which would let us do `array-contains` on a single field instead of two separate queries. Not worth the migration effort right now.
- MessageDto has all fields nullable (Firestore deserialization requirement) which means the mapper has to handle nulls with fallback defaults. Not ideal but thats how Firestore works with Kotlin data classes.
- No pagination on `observeMessages` — it loads all messages in a conversation. With very long conversations this could become a performance issue. Would need `limit()` + cursor based pagination if it ever gets to that point.
