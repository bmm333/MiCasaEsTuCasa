## Admin Domain - Role-based Access Control
## Status
Accepted

## Context

The application requires an administration panel to handle: Keywords per catalogue, suspending/banning users, reviewing reports, statistics aggregated by bookings.
Main problem is the access controll: this operations should be accessed exclusivley by user with Admin role type. Firestroe Security provides the server side safety, but requires an additional field `roles` in user document, adding coupling.
Second question in order is the protection of destructive operations:
Such as Permanent ban , suspension, deleting keywords , irreversible or high impact operations. The system should prevent accidental errors and abuses like self ban or admin banning admin.

## Decision

Layered Protection for admin operations:
1. UseCase Level: each use case calls `userRepo.getCurrentUser()` and verifies that `user.Role.contains(UserRole.ADMIN)` before proceding. Returns `SecurityException` if the check fails. Fails fast without even calling Firestore.
2. Repo Level: `FirebaseAdminRepo` dose not verify the role (delegates to usecase) but each operation is on separate collections that security rules protect.
3. Firestore Security Rules: the rules read the user document to verify the role. This is the server side protection. bypassing every client side manipulation.

Specific protection from destructive operations:
-   An Admin cannot suspend or ban itself.
-   An Admin cannot suspend or ban another admin.
-   `getAllKeywords` dose not Require Admin role , since keywords are public data used by the Search.

**`UserStatus`**
    Added `Active/Suspended/Banned`. On Login `AuthViewModel` needs to verify that the user has status active befroe navigati to home. otherwise throwing the specific message.e

**Bookin Statistics**
Calculated client side with `getBookingStats()` gets all bookings and counts per status. Simple and correct , but will ofcourse not scale.e

## Consequences

**Pros**
- No exposed endpoint all via Firestore + Security Rules
- Layered Protection
- Protection at domain level
- Keyword accesible to everyone with no privileges.

**Cons**
security rules with get per user document cost per read. with few admins the cost is relativley low. 
- roles as List<String> Not Strongley typed , need anothe solution , since the smalles typo could render an admin to non admin.
