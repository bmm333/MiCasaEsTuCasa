## ADR-008 Role Synchronization and UI Persistence (DataStore)

### Status
Accepted

## Context
We had a major UX bug in the profile screen. When a normal user created their first property, they were supposed to be promoted to the `OWNER` role and see the Host Dashboard. Instead, they kept seeing the "Host your home" banner. 

There were three separate issues causing this:
1. **Security Rules blocking the update (Root Cause)**: Our Firestore rules were preventing users from updating their own `roles` array, so the promotion silently failed in the background.
2. **UI Flash (Network Latency)**: Every time the user opened the Profile screen, the UI would wait for the Firestore `getUser` call to complete. Until it finished, it defaulted to `isHost = false`, causing a nasty UI flash.
3. **UI heavily dependent on network state**: The UI relied purely on `user?.roles?.contains(UserRole.OWNER)`. If the network was slow or the rule failed, the user was treated as a guest even if they had active properties in the database.

## Decision
We fix this by tackling the backend rules, the repository logic, and local caching with Jetpack DataStore.

**1. Security Rules Update**
We updated `firestore.rules` to explicitly allow users to update their own profile, with a strict check to prevent them from adding the `ADMIN` role.
```javascript
allow update: if request.auth.uid == userId
    && !request.resource.data.roles.hasAny(['ADMIN'])
```

**2. Selective Role Updates in Repo**
Instead of overwriting the whole `User` document, we added `updateUserRoles` to `FirebaseUserRepo` which uses `.update("roles", ...)` to specifically target the array. This happens inside `CreatePropertyUseCase` when the property is successfully saved.

**3. Jetpack DataStore for UI Persistence**
To fix the layout flash, we added `androidx.datastore:datastore-preferences`. 
In `UserViewModel`, we expose an `isHost` StateFlow that reads a boolean directly from DataStore (`IS_HOST_KEY`). Because DataStore is fast and local, the `ProfileScreen` knows immediately if the user is a host, without waiting for the network.

**4. Edge Case Handling (Demotion)**
If a user deletes all their properties, `PropertyViewModel` calls a new `DemoteHostUseCase`. This removes the `OWNER` role from the backend and sets the DataStore `isHost` to false. 
Also, `UserViewModel.loadUser` double checks the real world: if the DB says they aren't an owner but they actually have properties, it fixes the DB and DataStore automatically.

## Consequences

**Pros**
- Zero UI flash when opening the profile. The dashboard shows up instantly.
- The root cause (security rules) is fixed securely. A normal user still cannot make themselves an admin.
- Clean Architecture is preserved (DataStore is injected via Hilt, use cases handle the business logic of demotion/promotion).

**Accepted Tradeoffs**
- Adding the DataStore library just to save a single boolean (`is_host`) might feel like overkill, but the UX improvement (removing the layout flash) makes it worth it.
- If a user logs into a brand new device, they might see the flash exactly once while `loadUser()` syncs the DataStore for the first time.

**Technical Debt**
- Right now DataStore is only caching `is_host`. Ideally, we should probably cache the entire `User` object locally using Room or DataStore to provide a full offline-first experience, but that requires a lot more mapping and serialization which is out of scope for now.
