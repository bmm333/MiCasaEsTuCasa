# ADR 009: Account Deletion and Moderation Strategy (Soft-Ban vs Hard-Delete)
## Context
As the platform grows, we need a secure and legally compliant way to handle malicious users (bans) as well as honor user requests to permanently delete their accounts and all associated data. However, deleting a user entirely from the system during a moderation ban would destroy evidence needed for investigations and disrupt active bookings. 

### Our Solution
We implemented a dual-strategy approach separating moderation (bans) from user-initiated account deletion.

1. **Moderation (Soft-Ban)**: When an admin bans a user, we execute a "credential burnout". We use the Firebase Admin SDK to set `disabled: true` on their Firebase Auth account, instantly locking them out. However, we DO NOT delete their Firestore data. Instead, their `isOnHold` flag is set to `true`, which cascades to lock their properties from being booked or seen by the public, while keeping the data accessible for admins.
2. **Permanent Account Deletion (Hard-Delete)**: When a user intentionally deletes their account from the Settings screen, they must re-authenticate (for security). Then, a Cloud Function trigger (`functions.auth.user().onDelete()`) automatically fires on the backend. This trigger cascades and completely wipes out all their properties, messages, bookings, reviews, and Storage photos.

## Consequences 
 ## **Pro**
 - Security: Banned users are locked out at the authentication level (Firebase Auth), making it impossible to bypass UI restrictions.
 - Integrity: Soft-bans preserve chat histories and booking logs for admin investigation.
 - Compliance: Hard-deletes via Cloud Functions ensure that no orphaned data (like profile photos or old messages) is left behind, respecting user privacy.
 - Consistency: Cloud Functions handle the cascading delete on the backend, removing the risk of the mobile client dropping the connection halfway through a massive deletion process.

## **Cons**
 - Complexity: Required setting up a new Cloud Function and handling the re-authentication exception (`FirebaseAuthRecentLoginRequiredException`) in the UI.
 - Maintenance: If we add new collections in the future (e.g., a new feature), we must remember to update the `onUserDeleted` Cloud Function to include it in the cascade.

**Technical Debt**
- The cascading delete function currently deletes documents in batches. If a user has millions of messages, the Cloud Function might hit the execution time limit (9 minutes). We may need to implement a chunked or recursive background deletion task in the future if data scales massively.
