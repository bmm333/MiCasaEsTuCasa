# ADR 010: Modern Google Sign-In Integration (CredentialManager API)
## Context
We needed to implement Google Sign-In for the authentication flow. The traditional `GoogleSignInClient` API provided by Google Play Services is now officially deprecated and being replaced by the Android 14 `CredentialManager` API, which unifies passwords, passkeys, and federated sign-in under a single system-level prompt. 

### Our Solution
We bypassed the deprecated libraries and directly integrated the `androidx.credentials:credentials` and `com.google.android.libraries.identity.googleid:googleid` libraries.

1. **UI Layer**: We built a `GoogleSignInButton` component that leverages `CredentialManager.getCredential()`. It configures a `GetGoogleIdOption` using our Web Client ID and requests a `CustomCredential` from the system.
2. **Domain/Data Layer**: The resulting `CustomCredential` is parsed into a `GoogleIdTokenCredential`, and the underlying ID token is passed to `SignInWithGoogleUseCase`, which delegates to `FirebaseAuthRepo`.
3. **Backend Integration**: The Firebase Auth SDK exchanges this ID token for a Firebase credential (`GoogleAuthProvider.getCredential(idToken)`), seamlessly bridging the native Android CredentialManager with our Firebase ecosystem.

## Consequences 
 ## **Pro**
 - Future-proof: We are using the officially recommended Android API, meaning we won't have to refactor this when the old SDK is completely sunset.
 - UX: The `CredentialManager` API provides a sleek, bottom-sheet system UI that is highly trusted by users and supports passkeys out of the box if we decide to implement them later.
 - Clean Architecture: The Android-specific `CredentialManager` logic is isolated strictly in the UI component layer, while the Domain layer only knows about standard Kotlin Strings (the ID token).

## **Cons**
 - Complexity: The new API is heavily asynchronous and returns a raw `CustomCredential` that requires manual casting and parsing (e.g., `GoogleIdTokenCredential.createFrom()`), which caused initial integration friction.
 - Device Requirements: It requires up-to-date Google Play Services on the device/emulator to function correctly.

**Technical Debt**
- Error handling in the UI currently surfaces raw exceptions via Toasts. We should eventually map these specific `CredentialManager` exceptions (e.g., `NoCredentialException`, `GetCredentialCancellationException`) to localized, user-friendly error messages in the `AuthUiState`.
